# ClosedBook 設計メモ

作成：2026-11-16
状態：概念メモ。未着手。実装方式・公開範囲は未決定。

## 1. 概要

海外で話題になった学習法を、プロトコルとして実行できるプラットフォームにする。

方法の骨子（出所：ユーザーが共有した投稿）:

1. いきなりAIに要約させない。まず、その分野の定番教科書・論文・授業資料を集めて「信頼できる知識ベース」を作る
2. 資料に基づいて、AIに3つの質問だけをする
   - 中核的な共通認識（基礎概念・原則・全体の枠組みと関係）＝知識の骨格
   - 根本的な論争3つ（各立場の見解・根拠・反論）＝理論の限界
   - 中核概念・因果関係・応用・論争を網羅するテスト問題10問（答えは出さない）
3. 資料を閉じて自力で答える → AIに1問ずつ採点させる → 「抜けている重要な点」「結論を覚えただけで理解していない箇所」を指摘させる

一言で言うと、**AIに読ませるのではなく、AIに学習の難度を上げさせる**ための実行マシン。AIは地図を整理し、学習者は自分の足で歩く。

## 2. 設計原則

- **Grounding 必須**：AIの回答はアップロード資料だけに基づく。出典引用を必須とし、資料外の知識で水増ししない
- **答えの秘匿**：テスト問題の生成と同時に模範解答を作るが、採点が終わるまで学習者には絶対に見せない（データとして分離保管し、UI・プロンプトの両方で漏らさない）
- **資料ロック**：テスト回答中は、資料ビューアとAIチャットを無効化する。「閉じて答える」を仕様で強制する
- **採点の観点は正誤より「抜けと浅さ」**：点数よりも「どの重要な点が抜けたか」「どこが結論の暗記で止まっているか」を主出力にする
- **順序の固定**：フェーズは順番にしか進めない。スキップは「記録つきスキップ」としてのみ許可する（飛ばした事実自体を学習記録に残す）
- **論争を捏造しない**：資料に本物の対立がない分野では、論争フェーズは「資料内に根本的論争は見当たらない」と正直に出す。無理に3つ作らない

## 3. 学習プロトコル（中核仕様）

### Phase 0：資料ベース構築

- 入力：教科書・論文・スライド等（PDF / テキスト / Markdown）。分野ごとに「プロジェクト」としてまとめる
- 処理：チャンク分割、埋め込み、出典メタデータ（資料名・ページ・章）の保持
- 出力：資料一覧とカバレッジ表示（冊数・総量）。「資料が薄い」場合は警告を出す（骨格の質は資料で決まるため）
- 完了条件：最低限の資料が登録されていること（下限は要検討。目安：複数ソース）

### Phase 1：骨格（知識マップ）

- 質問（固定）：「この分野で広く受け入れられている中核的な共通認識には、どんなものがある？ その基礎となる概念、重要な原則、全体の枠組みを整理し、これらの知識の関係を説明して」
- 出力：要約文ではなく**構造**。概念ノード（土台／中核／枝葉の3層）＋関係エッジ（前提・因果・対比）＋各ノードへの出典リンク
- 目的：どこが土台でどこが枝分かれかを見て、時間をかける場所を決める

### Phase 2：論争

- 質問（固定）：「この分野で現在、根本的な論争が3つあるとしたら、それぞれ何？ それぞれの立場の見解、根拠、反対する理由を説明して」
- 処理：資料間の主張の矛盾・対立を検出し、立場ごとに整理する。各立場には必ず出典をつける
- 出力：論争カード×最大3（立場A／立場B／それぞれの根拠／反論／未決着の理由）
- 注意：設計原則どおり、対立が資料に実在しない場合は捏造しない

### Phase 3：テスト

- 質問（固定）：「これらの資料に基づいて、中核的な概念、因果関係、実際の応用、主要な論争を網羅するテスト問題を10問作って。まずは答えは出さないで」
- 生成時に模範解答と採点ルーブリック（観点：正確さ／網羅性／因果の理解／応用）を併せて作り、秘匿側に保管する
- 回答フェーズ：資料ロック状態で1問ずつ（または一括で）記述回答
- 採点：1問ずつ、ルーブリック観点別に評価。主出力は以下の2点
  - 抜けている重要な点（資料の該当箇所への引用つき）
  - 「結論を覚えただけ」の箇所：用語や結論は合っているが、なぜそうなるか・どういう条件で崩れるかが書けていない部分を特定する
- 追撃（任意）：浅いと判定された箇所には「なぜ？」「条件が変わったら？」の追加質問を1つ出す

### Phase 4：穴の追跡

- 採点で見つかった「抜け・浅さ」を **Gap（理解の穴）** として概念単位で記録する
- 次回セッション開始時に未解消の Gap を提示し、関連資料の再読範囲（出典ページ）を案内する
- 再テスト（該当概念だけの小問）で解消を確認し、Gap を閉じる
- 分野ごとの「穴の残数」がダッシュボードの主指標になる

## 4. データモデル（案）

| 対象 | 主な項目 |
|---|---|
| Project | 分野名、説明、作成日、現在フェーズ |
| Source | 資料名、種別（教科書／論文／スライド）、ファイル、ページ数 |
| Chunk | 本文、Source参照、ページ・章、埋め込みベクトル |
| KnowledgeMap | ノード（概念名、層、説明、出典）、エッジ（関係種別、出典） |
| Controversy | 論点、立場[]（主張、根拠、反論、出典）、未決着の理由 |
| Question | 問題文、観点タグ（概念／因果／応用／論争）、模範解答（秘匿）、ルーブリック |
| Attempt | 回答文、回答日時、資料ロック下で回答したか |
| Grade | 観点別評価、抜けリスト、浅さの指摘、追撃質問 |
| Gap | 概念、内容、状態（未解消／再テスト中／解消）、発生元Grade、再テスト履歴 |

## 5. AI処理の設計メモ

- 各フェーズは構造化出力（JSON Schema）で受け取り、画面描画と保存を分離する
- 骨格・論争は「資料のどこに基づくか」を全主張に要求する。出典のない主張は下げる／落とす
- 論争フェーズは生成よりも**検出**寄り：資料ペア間の主張対立を先に洗い出してから文章化する
- 採点は生成モデルと同一でよいが、プロンプトには模範解答・ルーブリック・ユーザーの回答だけを渡し、雑談文脈を持ち込まない
- 「結論を覚えただけ」の検出：回答内の主張について、理由・条件・反例のいずれかが欠けているものを機械的に拾い、最後にLLMで確かめる二段構え

## 6. 画面フロー（案）

1. 分野一覧（プロジェクト、フェーズ進捗、穴の残数）
2. 資料管理（アップロード、カバレッジ警告）
3. フェーズ画面（骨格マップ／論争カード）
4. テスト画面（ロック表示つき、資料・チャット無効）
5. 採点結果（観点別、抜けと浅さ、出典へのジャンプ）
6. 穴リスト（未解消の Gap、再テスト開始）

## 7. 既存サービスとの差分

近接は Google NotebookLM（資料アップロード、出典つきチャット、クイズ生成まで既にある）。本企画の存在意義は被らない部分に限る。

- 手順の固定と強制（3つの質問を順に進める、テスト中は資料を開けない）
- 採点の主眼が正誤ではなく「抜けと浅さ」
- 理解の穴をセッションをまたいで追跡し、再テストで閉じる仕組み

汎用資料チャットは作らない。それは NotebookLM の領分。

## 8. MVP範囲

やること：

- 1ユーザー（自分用）前提
- 資料取り込み（PDF／テキスト）、プロジェクト1分野から
- Phase 1〜3 の固定プロトコル実行と保存
- Gap の記録と一覧、再テスト

やらないこと（MVPでは）：

- 汎用チャット、資料外QA
- 複数ユーザーのアカウント・課金・公開
- 音声・動画資料の取り込み

## 9. 技術構成（未決定）

候補A：Next.js + Supabase（Postgres + pgvector）+ LLM API
候補B：Muse の Space（フルスタック）で試作し、手応えを見てから移植
候補C：Hono + Cloudflare 一式（2026-11-16、本人の提案。実現可能性を確認済み）

- API・画面配信：Hono on Workers
- リレーショナルデータ（Project / Source / Question / Attempt / Grade / Gap）：D1（SQLite、1DB上限10GB＝自分用には十分。全文検索は FTS5 が使える）
- 原本ファイル：R2（署名付きURLで直接アップロードし、Workers のリクエスト上限を回避）
- ベクトル検索：**Vectorize**（D1 にはベクトル検索がないため、これだけ追加で要る）
- 埋め込み：Workers AI（bge系）または外部API
- 生成・採点：外部LLM APIを fetch で呼ぶ（待ち時間は Workers の CPU 時間に数えられない）。長い処理は Queues で非同期化
- 認証：自分用なら Cloudflare Access で足りる

候補Cの難所は1つだけ。PDFのテキスト抽出。Workers はメモリ128MBで、pdf.js 系は重い。unpdf でテキスト主体のPDFは処理できる実績があるが、重いPDFはブラウザ側で抽出してから送るか、Queues で分割処理する。スキャン画像PDFのOCRは Workers 内では扱わない（MVP範囲外）。

いずれでも、RAG の検索品質と構造化出力の安定性が本体。UI は後。

## 11. リスク

- 採点が甘いと「理解した気分」だけが残り、方法の核心が崩れる。ルーブリックと出典照合を厳しめに倒す
- 資料が少ない・偏っていると、骨格マップ自体が歪む。Phase 0 の警告を軽く扱わない
- 論争の捏造。設計原則で禁止済みだが、生成側の癖として出やすいので出典必須を徹底する

## 12. 公開形態：セルフホスト型OSS（方針決定 2026-11-16）

SaaS として運営するのではなく、利用者が自分の Cloudflare アカウントにデプロイして使う形で公開する。この選択で設計が変わる点：

- **資料の権利問題が消える**：教科書・論文は利用者自身の環境（R2）にだけ置かれ、運営者は他人の資料を一切預からない。セクション10の「資料の権利」の懸念はこの形なら大幅に軽くなる
- **BYOK（Bring Your Own Key）**：LLM の API キーは利用者が自分のものを設定する。運営者に推論コストが乗らない。エンドポイントは OpenAI 互換で差し替え可能にしておく（公式APIでも、ゲートウェイ経由でも使える）
- **マルチテナント設計が不要**：1デプロイ＝1ユーザー前提でよい。アカウント管理・課金・テナント分離は作らない。スコープが大きく縮む
- **デプロイの簡単さ自体がプロダクト価値になる**：wrangler での数コマンドデプロイ、D1 / R2 / Vectorize の作成とマイグレーションの同梱、つまずきどころ（PDF抽出まわり等）の README への明記
- **データは利用者のもの**：学習記録（Gap・採点結果）を JSON / Markdown でエクスポートできること。セルフホストを選ぶ層はここを気にする
- **認証は軽く**：自分の環境前提で、Cloudflare Access の任意設定で足りる
